## Source-level summary grounding

The observed label hallucination is now prevented in the application source, rather than merely documented:

- Tables, objects and lists are described deterministically from their executed fields. No model-generated row labels or identities are accepted, and summary_mode is deterministic-structured
- Non-numeric scalar values are also rendered directly
- Numeric scalar model summaries must mention the executed value and use only supported numeric claims, including number words and literal query parameters. Unsupported numeric facts, absent computed totals or invented scalar product labels trigger a disclosed deterministic-fallback
- Responses expose summary_mode and model_summary_rejected. Query generation and AST/seccomp validation are unchanged
- This summary guard does not repair analytical mistakes in generated code. The original wrong-direction ranking query must still fail independent verification, even when its returned table is now described honestly
- Literal-number checks do not establish complete semantic correctness; unit/meaning and query-intent verification remain important

The ranking question was rerun through the actual local model after this guard. Its generated query still failed independent direction/identifier verification (0/1 query acceptance), but the returned response used deterministic-structured wording from the executed fields and introduced no invented product labels. This is a successful summary-grounding regression, not a rescued analytical pass. The bounded rerun took approximately 15 seconds and made one genuine model-generation request; no model summary request was sent for the table.

## Narrow post-execution ranking-intent check

The application now independently checks unfiltered individual item/product/SKU questions asking for lowest/highest stock quantity. It uses schema aliases only when a metric is unambiguous, recognized unique source identifiers, and the source workbook's numeric ranking. No deterministic answer or planner is substituted.

- Returned identifier/metric pairs must exist together in the source. Unknown identifiers, changed item labels, omitted metric/identifier fields, duplicated items, wrong direction, wrong prefix size or incorrect prefix membership are rejected
- Missing and non-finite quantities are excluded. Genuine ties at the cutoff may use any corresponding source identifier, while all items strictly ahead of the cutoff must remain present
- An explicit numeral or supported count word determines the prefix size; otherwise the check establishes correctness only for the returned prefix size
- Filtered warehouse/category/supplier questions, grouped aggregation, unclear metrics, ambiguous stock columns, missing unique identifiers and incomplete bounded output remain inconclusive. Category/supplier rankings without individual-item intent are not applicable
- analysis_validation records passed, inconclusive or not_applicable, with reasons. rejected=true distinguishes a rejected generated answer from cases where this narrow check cannot decide
- A rejected answer enters the existing single model-correction attempt. A second failure is disclosed with result withheld; neither validation nor feedback supplies a replacement answer
- AST/seccomp execution and summary grounding are unchanged. The check is not a general semantic verifier and does not cover arbitrary calculations, filtered rankings or joined datasets

The actual tiny local model was rerun after this intent guard. It omitted source item identifiers, and its one correction introduced unsupported return syntax. Query acceptance remains 0/1; the invalid result was withheld rather than displayed as the requested ranking. This is an actual model-quality failure recorded separately from successful safety enforcement. Two genuine model generations completed in approximately 26 seconds, with no planner substitution, summary fabrication or outbound workbook transmission.

## Reproducible execution

These optional dependencies are separate from requirements.txt. A fresh Linux environment can be prepared with Python 3.12 and the measured torch/transformers/safetensors versions; use PyTorch's official CPU wheel index for torch. The evaluation here reused .hwr-venv without changing the baseline app environment.

To retrieve the public pinned snapshot explicitly without authentication, install the model's Hugging Face dependencies and use:

    from huggingface_hub import snapshot_download
    snapshot_download(repo_id="Qwen/Qwen2.5-Coder-0.5B-Instruct", revision="ea3f2471cf1b1f0db85067f1ef93848e38e88c25", token=False, local_dir="data/private/models/qwen2.5-coder-0.5b-instruct", allow_patterns=["config.json", "generation_config.json", "tokenizer_config.json", "tokenizer.json", "vocab.json", "merges.txt", "model.safetensors", "LICENSE", "README.md"], max_workers=3)

Set HF_HUB_DISABLE_IMPLICIT_TOKEN=1 and HF_HUB_DISABLE_TELEMETRY=1 while downloading. Downloading public weights is a setup operation; workbook data is never part of that request. The serve command subsequently runs offline from local files only.

The optional scripts/evaluate_inventory_llm.py has two commands:

1. serve loads an already-downloaded local model with trust_remote_code=False, local_files_only=True and use_safetensors=True. It binds only 127.0.0.1, disables model-hub network/implicit authentication/telemetry, uses bounded CPU threads and generation token/time limits, and caps memory and process CPU usage
2. evaluate calls the unchanged OpenAI-compatible adapter and InventoryAgent against the supplied workbook. Actual model-generated plans go through the existing AST/seccomp sandbox. The one permitted model correction attempt remains enabled; no deterministic-planner substitution is permitted

If the model returns exactly one Python expression, InventoryAgent may mechanically bind that unchanged expression to result. It retains raw_model_code and code_normalized provenance and displays a normalization warning. Arbitrary statements, markdown and malformed code receive no such conversion. The resulting code still passes the same validation, OS sandbox and resource limits; unsafe expression calls remain blocked.

Example local server:

    .hwr-venv/bin/python scripts/evaluate_inventory_llm.py serve --model-dir data/private/models/qwen2.5-coder-0.5b-instruct --threads 2 --serve-seconds 900 --trace-dir outputs/private_samples/local_llm_generations

The ordinary application can connect to this already-running loopback service with LLM_BASE_URL=http://127.0.0.1:8766/v1 and LLM_MODEL=Qwen/Qwen2.5-Coder-0.5B-Instruct. No API key is needed for this local-only example. Enable the configured model in the sidebar before querying.

The evaluate command accepts a workbook path, quantity/value/identifier column names, header row, reference-column range and private output location as arguments. Verification derives expected values independently through direct pandas; model plans and generated summaries are recorded privately. Public reporting contains only aggregate success counts and limitations.

## Acceptance and limitations

- Generation must be attributable to the actual loaded model, never a fixture or synthetic planner
- Generated queries must pass the unchanged sandbox and match independent pandas results
- A summary being returned does not establish factual correctness. The evaluator checks literal-number consistency and independent expected scalars, then requires manual inspection of meaning, units, rankings and unsupported categorical claims. This review rejected the ranking answer despite its use of returned quantities
- The tiny CPU candidate may fail JSON formatting, column selection, reasoning or instruction adherence. A failed small-model trial does not justify weakening the sandbox or claiming open-ended competence
- No workbook content is transmitted outside this machine; no paid provider calls or credential discovery occur
- Handwriting-model experiments are separate from this Q1 evaluation
